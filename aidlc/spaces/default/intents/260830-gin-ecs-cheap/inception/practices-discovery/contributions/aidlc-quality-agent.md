## Contribution

QA 観点で LEAD ドラフトの `## Testing Posture` を検証した。結論として、単独開発・学習/実験目的の低コスト・エフェメラルなインフラプロジェクトに対して、ドラフトのテスト方針はおおむね「適正サイズ（right-sized）」である。テストピラミッド（ユニット多め・E2E 最小）と test-strategy の Minimal 相当（要件駆動・happy-path 中心・厳格なカバレッジ下限なし）に整合しており、ceremony を過剰に積み上げていない点は妥当。以下、統合できる具体的な補強と、インタビューで解決すべきギャップを示す。

### テスト方針の評価（適正サイズか）
- **Methodology: test-after / Ordering** の明記は良い。ハードコードデフォルト（methodology 未確定時は test-after）とも一致し、`memory/*.md` が空の現状で矛盾はない。学習インフラタスクとして TDD/BDD を強制しないのは合理的。
- **カバレッジ下限なし**の判断は Minimal 戦略に沿う。ただし「無下限」＝「測らない」ではないことを明確化したい。数値ゲートは課さなくても、`go test -cover` でカバレッジを可視化（レポート出力のみ、ブロックしない）しておくと、学習目的にも合致し将来の引き上げが容易。これは coverage/tooling 補足であり methodology を変えないため strict-additive で追加可能。
- ピラミッド観点で、このプロジェクトの E2E 相当は「デプロイ後スモーク」で代替されている。専用の重い E2E スイートを持たない選択は適正。スモークをパイプラインの完了条件に据えている点は「shift left, but do not skip right」を満たす。

### テスト層ごとの補強（統合可能）
- **Go ユニット**: `net/http/httptest` を使い Gin ハンドラをプロセス起動なしでテストできる旨を1行加えると、実装者の迷いが減る。happy-path 中心は妥当だが、`/healthz` 以外にハンドラが増えた際の最低限のエラーパス（4xx を返す分岐）を「1 ケースだけ」目安にするとセーフティネットが締まる。
- **Terraform**: `terraform validate` / `plan` を CI で回すのは静的検証として妥当。ただし plan は「差分の可視化」であり合否判定ではない点を注記したい。学習用途では `tflint`（現状 task 化されていない）を任意にとどめる判断でよいが、必須/任意はインタビューで確定すべき（下記ギャップ参照）。`terraform test`（Terraform 1.6+ のネイティブ機構）は学習目的なら明確にスコープ外でよい。
- **スモークテスト**: 「健全に応答」の合否基準が曖昧。最低限、対象エンドポイント（`/healthz` 等）・期待 HTTP ステータス（200）・タイムアウト/リトライ回数・判定コマンド（例: `curl --fail` の終了コード）を1行で定義すると、テストが self-documenting かつ再現可能になる。これはドラフトの意図を壊さない具体化。
- **エフェメラル運用との整合**: create/destroy モデルでは「環境が立っている短時間の間にスモークが通ること」がデプロイ完了の唯一の品質ゲートになる。この単一ゲートが壊れるとパイプライン全体の信頼性が落ちるため、スモークは冪等・独立・タイムアウト付きで、失敗時に destroy まで到達できる（テスト失敗が環境の放置＝コスト超過を招かない）ことを保証したい。

### CI 品質ゲートの整合性
- `discovered-rules.md` の Mandated「`terraform fmt`・`validate` と Go のビルド/テストを CI で実行し失敗時マージブロック」は、`testing-guide.md` の Gate 1（マージ前: ユニット通過・lint 警告なし）と整合する。良い。
- ただし「テスト実行」と「テスト失敗でブロック」が Testing Posture 側の箇条書きに明示されていない。Deployment/discovered-rules に散在しているので、Testing Posture にも「CI の必須ゲート＝ビルド＋ユニット＋fmt/validate が緑であること」を1行で集約すると、品質ゲートの単一の参照点ができる。

### インタビューで解決すべきギャップ（QA 観点）
1. **カバレッジの扱い**: 完全に無測定にするか、`-cover` で可視化のみ行うか（ゲートは課さない前提）。
2. **`golangci-lint` / `tflint` の必須 vs 任意**: 品質ゲートをブロッキングにするか、警告のみにするか。evidence.md でも未解決として挙がっており、QA としても確定が必要。
3. **スモークテストの合否基準**: 対象エンドポイント・期待ステータス・タイムアウト/リトライ・失敗時の自動 destroy の有無。
4. **スモーク自動化の範囲**: create→smoke→destroy を CI で自動化するか手動運用か（evidence.md の未解決点と重なる）。品質ゲートの実効性はここに依存する。
5. **テスト失敗時のコスト保護**: スモーク/デプロイ失敗時に環境が残置されない仕組み（`always()` 相当の destroy ステップ）を必須にするか。¥1000/月目標に直結する品質×コストの交点。

## Positions

- AGREE: `Methodology: test-after` と Ordering の明記は Minimal 戦略・ハードコードデフォルトに整合し、学習インフラプロジェクトに適正サイズ。
- AGREE: 厳格なカバレッジ下限を課さない判断は妥当（ただし可視化のみの `-cover` 追加を推奨、methodology は不変）。
- AGREE: 専用 E2E スイートを持たずデプロイ後スモークを完了条件とする層構成は「shift left, do not skip right」を満たす。
- OBJECT: スモークテストの合否基準（対象・ステータス・タイムアウト・自動 destroy）が未定義のままで、現状ではテストが再現可能・self-documenting とは言えない。インタビューで確定すべき。
- OBJECT: `terraform plan` を検証手段として列挙しているが「plan は差分可視化であり合否ゲートではない」旨の注記がなく、品質ゲートとして誤読される余地がある。
